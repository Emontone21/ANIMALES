# Arquitectura

## Piezas

```
┌──────────────────────┐        ┌─────────────────────────────────────────┐
│  App Expo (RN + TS)  │ ─────▶ │  Supabase (nube)                        │
│  web en Vercel;      │ REST   │  Auth · Postgres (PostGIS, pgvector,    │
│  nativa más adelante │ RLS    │  pg_net, pg_cron) · Storage ("fotos"    │
│  (web instalable)    │        │  público, "capturas" privado) · Edge    │
│  MapLibre + OSM      │        │  Functions "reconocer" y "avisar"       │
│  TanStack Query      │        │                                         │
└──────────────────────┘        └──▲───┬───────────────────┬──────────────┘
┌──────────────────────┐ REST      │   │                   │
│ api/vista-previa.ts  │ ──────────┘   │                   │
│ función de Vercel:   │               │                   │
│ Open Graph para bots │               │                   │
└──────────────────────┘               │                   │
                                       │ reconocer: fotos  │ push nativo (pg_net)
                                       │ (mediana) y datos │ y web (avisar,
                                       │ del animal        │ Web Push cifrado)
                        ┌──────────────▼──────────┐   ┌────▼──────────────────┐
                        │ API de Claude           │   │ Expo Push API         │
                        │ (Anthropic)             │   │ y servicios de push   │
                        │ claude-haiku-5-5        │   │ de los navegadores    │
                        └─────────────────────────┘   │ (FCM, Mozilla, Apple) │
                                                      └───────────────────────┘
```

- La app habla directo con Supabase. Lee con RLS. Escribe directo solo en lo personal (perfil propio, seguimientos, denuncias, mensajes, notificaciones, tokens, bloqueos), con UPDATE limitado por columna; `animales`, `avistamientos`, `cambios_estado`, `contactos_resguardo` y `reportes_errores` solo se escriben por funciones SQL `security definer` que validan las reglas.
- Casi no hay servidor propio: lo que no puede confiar en el cliente vive en Postgres (RPC y triggers). Las llamadas salientes (las funciones `reconocer` y `avisar`, Expo Push) se hacen con `pg_net` desde triggers y pg_cron.
- Hay tres piezas de servidor propias:
  - `api/vista-previa.ts`, una función de Vercel que arma la vista previa del link de un caso o de una historia del muro de reencuentros para WhatsApp, Facebook, Telegram y otros. Solo lee, con la clave pública de la app (la publishable o, de respaldo, la anon); `vercel.json` le manda únicamente los pedidos de bots.
  - `supabase/functions/reconocer`, una Edge Function de Supabase (Deno) que hace el reconocimiento con la API de Claude: describe cada foto, pide a la base pocos candidatos y le pide a Claude que la compare con ellos. La llama la base con `pg_net`.
  - `supabase/functions/avisar`, otra Edge Function que manda las notificaciones del celular en web (Web Push, con `@negrel/webpush`, MIT): cifra cada aviso para cada navegador suscripto y lo firma con las claves VAPID. La llama la base con `pg_net` cuando hay avisos nuevos.
- El servicio de embeddings en Python (`services/vision`) queda en el repo sin desplegar, como alternativa documentada (`docs/DECISIONES.md`).

## Flujos

**Publicar.** Primero se elige qué pasó: "Perdí a mi animal" (lo publica su familia) o "Encontré un animal". La app comprime la foto (JPEG, 1280 px), la sube a `fotos/<uid>/<uuid>.jpg` con su miniatura cuadrada de 320 (`<uuid>.miniatura.jpg`) y su versión mediana (`<uuid>.mediana.jpg`, la foto entera a 640 px de lado mayor, que ve la IA) al lado, y llama a `publicar_animal` con `p_tipo`, que inserta el animal y su primer avistamiento en una transacción: `encontrado` o `perdido` ("visto por última vez"). La RPC solo acepta una foto que exista en la carpeta del usuario dentro del bucket `fotos`, con ese nombre (`<uid>/<uuid>.jpg`), y que no esté en otro avistamiento (0023). Publicar y avisar "lo vi" tienen tope por hora y por cuenta (`publicaciones_por_hora_cuenta` y `avisos_por_hora_cuenta`, 10 y 30, en `config_app`). En un perdido guarda el nombre y el contacto que la familia decide mostrar, y redondea la ubicación a 3 decimales (unos 100 m), porque ese punto suele ser su casa. Quien publica sigue su caso automáticamente.

**Miniaturas.** Toda foto que se sube (reportes, avistamientos, resguardos y avatar) va con su miniatura: el centro de la foto, recortado cuadrado y llevado a 320 px. Y con su versión mediana: la foto entera, sin recorte, con el lado mayor a 640 px (`medidasMediana`), para el reconocimiento. La convención del nombre vive solo en `src/lib/imagenes.ts`; la base solo sabe que una foto y sus variantes comparten la ruta hasta el primer punto (`raiz_foto`). El mapa (foto en todos los marcadores), las tarjetas, "Cerca tuyo", la lista de casos, Mis reportes, los avatares y las fotos chicas del detalle usan la miniatura (`FotoMiniatura`); si no carga (fotos de antes de la Fase 8) o la ruta es una URL externa (datos de demo), la original. La base guarda solo la ruta de la original.

**Interactuar.** "Lo vi" llama a `registrar_avistamiento` (foto obligatoria, también de la carpeta propia). Resguardar, reunido y reabrir pasan por `cambiar_estado_animal`, que valida las transiciones permitidas y quién puede hacerlas, guarda el historial en `cambios_estado` y, al resguardar, crea un avistamiento (el "¿Dónde está ahora?" se guarda redondeado a 3 decimales, unos 100 m, porque suele ser la casa de quien lo tiene); el contacto que comparte quien lo resguarda va a `contactos_resguardo`. Cualquiera con cuenta puede resguardar; en un perdido, con una foto actual de la carpeta propia, que entra a la cola de reconocimiento. Un perdido solo lo marca como reunido o lo reabre su familia (quien lo publicó). Un encontrado lo marca como reunido, o lo vuelve a avistado ("se volvió a escapar"), quien lo publicó o quien lo tiene resguardado; reabrir un caso cerrado, solo quien lo publicó. Denunciar inserta en `denuncias`; a las 3 denuncias de cuentas distintas que tenían al menos 7 días al denunciar, la publicación se oculta sola.

**Reconocer.** Cada avistamiento con foto entra en `cola_vision`; cada vez que una fila de la cola queda pendiente (al entrar o al volver, por ejemplo cuando se corrige la especie), un trigger avisa a la función `reconocer` con `pg_net` (si `config_app.vision_url` está seteada y el reconocimiento está disponible) y espera hasta 60 s. Un trabajo de pg_cron (`vision-pendientes`, cada 2 minutos) llama a `/procesar-pendientes` solo si `cola_vision_pendientes` tiene filas: levanta los avisos perdidos y los reintentos. La función vacía la cola con un tope de 90 s. Toda llamada de la base a la función pasa por `llamar_vision`, con el header `X-Vision-Secret` (`config_app.vision_secret`, que la función lee de la base). Por cada foto, la función:
1. **La toma** (`tomar_pendiente_ia`: queda `procesando`, así dos pedidos no la procesan dos veces; si la función se corta, vuelve a la cola a los 10 minutos). Si el caso está cerrado, unido a otro u oculto, sale de la cola sin llamar a la API.
2. **La describe** con Claude (una llamada, con la foto entera a 640 px: la función baja la versión mediana del bucket o, si no está, la original, y la manda dentro del pedido; las fotos de otros sitios, que solo tienen los datos de demo, también las baja: `descargar.ts`, con el tipo que dicen sus bytes, JPEG, PNG, WebP o GIF, hasta 5 MB y 10 s, solo del proyecto o de los sitios de demo y sin seguir redirecciones, y si no, "foto no disponible"): si hay un animal y cuál, colores, patrón, tamaño, collar, raza aproximada, rasgos y calidad. La respuesta es una herramienta con esquema JSON estricto y se valida (`validar.ts`): los teléfonos, links y emails de sus textos (motivo, rasgos, lo que coincide y difiere, raza y color del collar) se tapan con "[dato oculto]", porque vienen de texto escrito en la foto, y la base los rechaza como última barrera (`tiene_datos_de_contacto`, 0023); si lo único mal es que el motivo o una lista de rasgos se pasan de largo, se recortan (el motivo a 140 en el último espacio, con "…"; los rasgos, los primeros 8 y cada uno a 80) y la llamada queda bien, con el aviso de cuánto se pasó en `detalle`; todo lo demás que no valida se rechaza. Se guarda en `descripciones_ia` (con modelo y tokens); un reintento no la vuelve a describir. Sin animal, o de otra especie que la del caso, no se compara.
3. **Pide los candidatos** a la base (`candidatos_ia`, hasta `max_candidatos`): misma especie, abiertos y visibles, a menos de `radio_coincidencia_m` con un avistamiento dentro de `ventana_coincidencia_dias`, perdido con encontrado o encontrado con encontrado (nunca perdido con perdido, ni un encontrado visto por última vez más de un día antes de la pérdida), sin los pares ya comparados ni los que ya tienen coincidencia, sin colores o tamaños claramente incompatibles y sin los que en su foto no se ve un animal; del más cercano al más lejano.
4. **La compara** con Claude en una sola llamada: la foto nueva, la foto de cada candidato (las dos enteras, a 640 px) y sus descripciones y datos declarados (tipo, tamaño, color y collar; nunca personas, contactos, mensajes ni la descripción libre). El pedido dice qué pesa: mucho el pelaje, las manchas, las orejas y la cara; poco el collar, el fondo, la pose y lo que escribió cada persona. Para cada candidato vuelve un veredicto (mismo, posible, distinto), `probabilidad_mismo` (de 0 a 100, la probabilidad de que sea el mismo animal: 0 seguro que no, 100 seguro que sí), un motivo de hasta 140 caracteres y los rasgos que coinciden y difieren. Una respuesta contradictoria ("distinto" con 50 o más, "mismo" con menos de 50) no vale y se reintenta. `guardar_comparacion_ia` guarda cada par en `comparaciones_ia` y crea la coincidencia solo si el veredicto es "mismo" o "posible" y la probabilidad llega a `umbral_ia` (0020), con `origen = 'ia'`, la probabilidad en `confianza` y el `motivo`, que avisa como siempre.

Cada llamada a la API se reserva antes (`iniciar_llamada_ia`, con los topes) y se registra después en `llamadas_ia` (tokens, costo estimado, modelo y resultado; si falló, el tipo y el texto del error de la API en `detalle`, hasta 300 caracteres y sin claves, URLs, emails, ids ni teléfonos: `limpiarDetalle`, 0019). Topes en `config_app`: `ia_activa` (interruptor general), `ia_tope_diario` (llamadas por día, hora de Montevideo; al llegar, las fotos esperan) y `ia_pausa` (la función la pone en `sin_credito` al quedarse sin crédito; la saca un moderador con **Reactivar**). Una respuesta que no valida, un 429, un 529 u otro error marcan la foto con error, y la cola la reintenta con espera creciente (5, 10, 20… minutos, hasta 8 intentos). Moderación ve el estado (configurado, apagado o pausado), la cola, las llamadas de hoy, el costo estimado del mes y los errores. Una persona confirma o rechaza con `resolver_coincidencia`: si el par incluye un perdido, solo su familia; entre dos encontrados, quien publicó cualquiera de los dos o un moderador. Confirmar vincula: los avistamientos del secundario pasan al principal, que es siempre el perdido o, entre dos encontrados, el más viejo. Si el secundario estaba resguardado y el principal no, el principal pasa a resguardado con el mismo contacto. Nada se fusiona solo.

**Gestionar un caso.** Quien publicó un reporte lo corrige o lo borra desde "Más opciones" en el detalle. Un caso sin autor o unido a otro no lo edita ni lo borra nadie.
- *Editar:* `editar_reporte` cambia especie, tamaño, color, collar y descripción y, en un perdido, nombre y contacto de la familia. El tipo, la ubicación y las fotos no se editan. Pide los términos vigentes, como publicar. Si cambia la especie, las coincidencias pendientes se descartan con sus avisos y las fotos del caso vuelven a `cola_vision`, para buscar con la especie corregida.
- *Borrar:* la app pide `fotos_del_reporte` (las fotos de su carpeta en el caso y en los reportes unidos a él, con sus miniaturas, menos las que algo fuera del caso usa), las borra con la API de Storage y llama a `borrar_reporte`. Esta usa `borrar_casos`, la misma función que `limpiar_cuenta` usa al borrar una cuenta: el caso y los reportes unidos a él, con todo lo que cuelga por cascada (avistamientos de cualquiera, historial, contactos, coincidencias, seguimientos, denuncias, conversaciones), y los avisos que llevaban a cualquiera de esas cosas. Las fotos de otras personas quedan en Storage, como al borrar una cuenta.

**Compartir.** El link de un caso es `<sitio>/animal/<id>`, con el sitio de `EXPO_PUBLIC_SITE_URL` (por defecto `https://spot-uy.vercel.app`). El botón Compartir del detalle abre la hoja del sistema (`navigator.share` en web, `Share` en nativo) con un texto armado según el tipo y el estado ("Se perdió Toby, perro marrón. Si lo viste, avisá acá:"). El color es texto libre: si trae números (podría ser un teléfono), no va en ese texto ni en la vista previa (`colorParaCompartir`, B37). Sin hoja de compartir (la mayoría de las computadoras) ofrece WhatsApp (`https://wa.me/?text=…`) y copiar el link. Los textos salen de `t.compartir` y el armado, de `src/lib/compartir.ts`.

**Vista previa del link.** La web es una sola página: todas las rutas devuelven el mismo `index.html`, sin datos del caso. Para los bots de vista previa, `vercel.json` reescribe `/animal/<id>` y `/reencuentros/<id>` a `api/vista-previa.ts` según el user-agent. La función lee el caso de `animales` con la clave pública (solo tipo, estado, nombre, especie, color, tamaño, collar, foto y si está oculto; con la publishable, solo en el header `apikey`, porque no es un JWT), pide el `index.html` del mismo deploy y le pone el título, una descripción armada con esos datos y la miniatura como etiquetas Open Graph y Twitter. Si el caso no existe, está oculto o se unió a otro, usa las genéricas. Nunca incluye el contacto, quién publicó, la ubicación ni la descripción libre. De una historia del muro lee `historia_reencuentro` (la misma RPC pública del muro): "Toby volvió a casa", "Volvió a casa después de 3 días. Mirá más reencuentros en Spot." y la miniatura de su foto; ni siquiera la frase. Si no existe o está oculta, las genéricas del muro. Si el pedido trae un caso y una historia a la vez, ninguno. Las personas siguen recibiendo el `index.html` estático, sin pasar por la función.

**Avisar.** La función `notificar` inserta en `notificaciones` y manda push a cada `push_tokens` del usuario vía Expo Push API. Triggers la llaman cuando aparece una coincidencia (si incluye un perdido, su familia recibe un aviso propio con el nombre: "Encontraron un animal parecido a Toby"), cuando alguien ve o resguarda un animal seguido, cuando un caso se cierra o reabre, y cuando llega un mensaje. Las RPC de errores la llaman cuando llega un reporte nuevo (a cada moderador) y cuando se resuelve (a quien lo mandó con su cuenta); `agradecer`, a cada persona que la familia agradeció. Cada aviso guarda quién lo causó (`actor_id`; en una coincidencia, quien publicó el otro reporte): no se manda a quien bloqueó a esa persona, y se borra si esa persona borra su cuenta. Los de "lo vieron" y de cambios de estado guardan qué pasó (`datos.evento`: visto, resguardado, reunido, reabierto). La pestaña Actividad se refresca sola; en web, además, llegan al celular (abajo).

**Notificaciones en el celular (web).** Cada navegador o app instalada que las activa guarda su suscripción de push en `suscripciones_push` (`guardar_suscripcion_push`, que solo acepta los servicios de push de Chrome, Edge, Firefox y Safari). El permiso se pide siempre con un toque: después de publicar ("¿Querés que te avisemos al celular cuando alguien lo vea?") o con el interruptor "Notificaciones en este celular" de Perfil; nunca al abrir la app. En iPhone solo con la app instalada; en los navegadores de WhatsApp, Instagram y Facebook se explica que hay que abrirla en Chrome o Safari; si se bloquearon, cómo volver a permitirlas (`formaDeAvisar.ts`). Cuando `notificar` crea un aviso para alguien con suscripciones, un trigger lo pone en `avisos_push` y despierta a la función `avisar` (`llamar_avisar`, una vez por transacción, con `X-Avisar-Secret`). La función le pide a la base qué mandar (`preparar_avisos_push`): descarta lo ya leído en Actividad, lo de alguien bloqueado, lo de un caso oculto (o una coincidencia con uno), uno del mismo caso o conversación en los últimos 5 minutos y lo que pasa el tope por persona y por hora (`config_app.avisos_push_por_hora`, 6); lo descartado sigue en Actividad. Con lo demás arma el texto de la pantalla bloqueada (sin nombres de personas, sin el texto de los mensajes ni direcciones: "Alguien vio a Toby", "Tenés un mensaje nuevo sobre Toby"), lo cifra para cada suscripción y lo manda con `Topic` y `TTL` de 12 h. El resultado vuelve a la base (`terminar_avisos_push`): una suscripción que el servicio da por vencida (404 o 410) se borra. En el celular, `public/sw.js` la muestra con un `tag` por caso o conversación (la nueva reemplaza a la anterior sin volver a sonar) y al tocarla abre el caso o la conversación. Al cerrar sesión, la app borra la suscripción de ese navegador. El push nativo (Expo) no cambia.

**Compartir en historias.** En el detalle de un caso abierto (solo web), junto a Compartir. La imagen de 1080 × 1920 se arma en el celular con un canvas, sin servidor (`src/features/historias/`, en un bloque aparte): la foto grande con esquinas redondeadas, "SE PERDIÓ" o "ENCONTRADO", el nombre o la especie, la fecha, el logo y "Ayudá a encontrarlo en Spot". El fondo es el color dominante de la foto, llevado hacia el claro o el oscuro hasta que el texto se lea (5,5:1). La foto se baja con `fetch` y se dibuja desde un `ImageBitmap`; si no se puede (una foto de otro sitio), sale con el color de la especie y la chapita. Nunca lleva contactos, quién publicó, la descripción ni dónde. Se manda con `navigator.share` como archivo y, en el mismo toque, se copia el link para el sticker de enlace de Instagram; si el navegador no puede mandar archivos (el de WhatsApp), se descarga.

**Reencuentros.** Los finales felices, siempre opcionales y solo de los perdidos (la familia es quien publicó el perdido; un encontrado reunido suma al contador pero no tiene historia).
- *Contar cómo volvió:* al marcar su perdido como reunido, la familia ve "¡Qué alegría! ¿Querés contar cómo volvió?" (una hoja con "Ahora no"); también después, desde "Cómo volvió" en el caso. El formulario (`/animal/<id>/reencuentro`, su propio bloque) pide una frase de hasta 280 caracteres, una foto del reencuentro opcional (si no, la del caso) con el aviso de que las personas que aparezcan estén de acuerdo, y si se muestra el nombre del animal. `guardar_historia_reencuentro` exige que sea la familia, que el caso esté reunido y no oculto y los términos vigentes; tapa teléfonos, links y emails de la frase con "[dato oculto]" (`ocultar_datos_de_contacto`, como los textos de la IA) y solo acepta una foto nueva de la carpeta propia que no use otra cosa. Devuelve los archivos de la foto anterior, que la app borra con la API de Storage. Editar es volver a guardar; borrar pasa por `fotos_de_la_historia` (la app borra la foto) y `borrar_historia_reencuentro`. Al borrar la cuenta, `limpiar_cuenta` borra sus historias y los agradecimientos que mandó o recibió.
- *Agradecer:* en el mismo formulario, `participantes_del_caso` lista, con su nombre público, a quienes participaron en el caso (todo el árbol de reportes unidos): avisaron que lo vieron, lo resguardaron o le escribieron a la familia; sin la familia ni nadie con un bloqueo en cualquier sentido. La familia marca a quién agradecerle y suma un mensaje opcional (hasta 280, también tapado). `agradecer` valida que cada persona haya participado, guarda una fila por persona y caso en `agradecimientos` (la segunda vez no hace nada) y avisa con `notificar` ("La familia de Toby te agradeció", tipo `agradecimiento`), que llega a Actividad y, por la función `avisar`, al celular. En Perfil, "Ayudaste a reunir a N familias" cuenta los casos que una familia agradeció (`familias_que_ayude`), sin los ocultos. Los agradecimientos los leen solo la familia y quien lo recibe: nada de esto es público.
- *El muro:* `/reencuentros`, sin cuenta. Arriba, `contador_reencuentros`: todos los casos reunidos, sin ocultos ni datos de demo (`es_foto_de_demo`: la foto es una URL de otro sitio); con menos de 5 dice "Los primeros reencuentros de Spot". Debajo, `muro_reencuentros`, de a 20, de la más reciente a la más vieja: la foto (la mediana), el nombre si la familia quiso (y si no parece un contacto: `nombre_publicable`), la especie, "Volvió a casa después de X días" (de la fecha del perdido a la del último cambio a reunido, en Montevideo: `datos_del_reencuentro`), la frase y la fecha. Nada de ubicación, quién publicó, quién ayudó ni contactos. `/reencuentros/<id>` muestra una (`historia_reencuentro`), con el muro a un toque. Se llega desde una tarjeta al final de "Cerca tuyo" ("34 volvieron a casa · Ver historias") y desde Perfil. Cada historia se comparte con su link (`linkDeHistoria`), con vista previa, y como historia de Instagram ("VOLVIÓ A CASA", la misma base de *Compartir en historias* con los días y la frase en dos líneas). Sus opciones son "Denunciar la historia" y, solo para la familia y moderación, "Ver el caso": la app lo ofrece si la tabla `historias_reencuentro` le devuelve la fila, que su RLS da solo a ellos (`useFamiliaOModeracion` y `opcionesDeHistoria`, en `muro.ts`).
- *Moderación:* una historia se denuncia aparte del caso (`denuncias.historia`); a las 3 denuncias de cuentas con antigüedad se oculta sola, y moderación la oculta o la vuelve a mostrar con `moderar_historia`. Oculta, o con el caso oculto, la ven solo la familia y los moderadores, sin compartir.

**Hablar.** `abrir_conversacion` crea (o reutiliza) una conversación entre dos usuarios sobre un animal, solo con quien publicó el caso (o un reporte unido a él) o con quien lo resguardó. Además, desde la 0014, quien publicó el caso o un reporte unido a él le puede escribir a quien avisó que lo vio en cualquier reporte del caso: en el Historial, cada aviso de otra persona lleva "Escribirle" (`aQuienesLoVieron` en `permisos.ts`). El caso es todo el árbol de reportes unidos, desde el principal. Una conversación que ya existe se puede retomar, así quien publicó le contesta a quien le escribió, y no se abren conversaciones nuevas sobre un caso oculto. Los mensajes se leen por polling cada 4 s mientras la conversación está en pantalla: la primera vez, todos; después, solo desde el último que llegó, con 10 s de margen para atrás (un mensaje que se guardó con una hora apenas anterior) y sin repetir los que vuelven a llegar (`src/features/mensajes/incremental.ts`, M20). Al marcarlos leídos se anotan también en la caché; la lista de conversaciones y las novedades, cada 20 y 30 s mientras Actividad está en pantalla, y el punto de "sin leer" de la pestaña pide solo si hay alguna, cada minuto. Nadie ve emails ni teléfonos. Si hay un bloqueo entre los dos, en cualquier sentido, no se abren conversaciones ni se mandan mensajes (lo validan `abrir_conversacion` y la política de INSERT de `mensajes`); quien bloquea desbloquea desde la conversación o desde Perfil.

**Ocultar.** Un moderador oculta o vuelve a mostrar un caso con `moderar_animal`; a las 3 denuncias de cuentas con antigüedad se oculta solo. Desde la 0014, un caso oculto lo ven solo quien lo publicó y los moderadores: la política de lectura de `animales` es `not oculto or creado_por = auth.uid() or es_moderador()`, y las de `avistamientos`, `cambios_estado`, `contactos_resguardo` y `coincidencias` (los dos lados) piden que se vea el caso. Las vistas tienen `security_invoker`, así que heredan la regla. Para el resto es como si no existiera: el detalle muestra "Esta publicación no está disponible." (el mismo texto que un caso que no existe), los avisos que llevan a él terminan ahí, el mapa no lo muestra y la vista previa del link usa las etiquetas genéricas. Las conversaciones que ya había siguen para sus participantes: `conversaciones_detalle` usa `left join` a `animales` y `animal_disponible` dice si quien consulta ve el caso (la app lo lee con `casoDisponible`, que sin la 0014 aplicada lo da por visible); si no, la conversación muestra "Publicación no disponible" y el aviso contra estafas. Volver a mostrarlo restaura todo, porque es la misma marca. Con el caso oculto, su historia del muro tampoco se ve (ni en el muro ni por su link) y no cuenta en "Ayudaste a reunir".

**Casos reunidos (0027).** Cuando el animal volvió, quien no participó en el caso ve solo lo básico: la foto, el nombre si la familia lo mostró, la especie, "Volvió a casa" y el link a su historia, si hay. Participaron, en cualquier reporte del caso: quien publicó un reporte, quien avisó que lo vio, lo encontró o lo resguardó, quien le cambió el estado, quien escribió en una conversación del caso antes de que se reuniera y moderación; si la familia bloqueó a alguien, esa persona ve lo básico. Lo decide `ve_detalle_del_caso` en las políticas de lectura de `avistamientos`, `cambios_estado`, `contactos_resguardo` y `coincidencias` (los dos lados), y las vistas lo heredan: `animales_detalle` llega con `reservado = true` y sin el resto, el mapa no trae el caso, el historial y las coincidencias llegan vacíos. La app muestra entonces `CasoBasico` (`soloLoBasico` en `permisos.ts`) y el mapa en grande vuelve ahí. Un reporte unido sigue a su caso principal. Si el caso se reabre, vuelve a verse todo, porque la regla mira el estado de ahora. Sin cuenta, nunca se participa: la vista previa del link también ve lo básico.

**Cuenta.**
- *Sesión:* el cliente usa el flujo PKCE (`flowType: 'pkce'`, auditoría 2). El botón de respaldo de Google (abajo) vuelve con `?code=`; Supabase lo canjea con el verificador que guardó este navegador al pedirlo (en web, solo al crear el cliente; en nativo, `crearSesionDesdeUrl`). Un link con tokens en el fragmento no abre sesión.
- *Google (web):* con `EXPO_PUBLIC_GOOGLE_CLIENT_ID`, Ingresar y Registrarse muestran el botón oficial de Google Identity Services, que dibuja Google ("Continuar con Google", `es-419`). `IngresoGoogle.web.tsx` va en un bloque aparte (`lazy`) y recién ahí baja `https://accounts.google.com/gsi/client` (`cargarGoogle`, `src/features/auth/scriptGoogle.ts`). Arma un nonce de 32 bytes (`prepararNonce`, `src/features/auth/google.ts`): Google recibe su hash SHA-256 en `initialize` (con `use_fedcm_for_prompt`) y lo pone en el token; al elegir la cuenta, `ingresarConTokenDeGoogle` llama a `signInWithIdToken` con el token y el nonce original, y Supabase compara los dos. No hay redirección: la pantalla de Google muestra el sitio, no `<proyecto>.supabase.co`. Si el script no carga en 10 s, falla o no hay ID de cliente, el botón de respaldo (`BotonGoogleRespaldo`), con `signInWithOAuth` y PKCE; la app nativa usa siempre ese. En los navegadores de WhatsApp, Instagram y Facebook, que Google no acepta, la pantalla explica que hay que abrir el link en Chrome o Safari y ofrece copiarlo (`formaDeIngresarConGoogle`).
- *Links de los mails:* van a `/auth/confirmar?token_hash=…&type=…` (signup, recovery o email_change) y sirven en cualquier navegador. `abrirLinkDeMail` (`src/features/auth/linkDeMail.ts`) los canjea con `verifyOtp` en un cliente de un uso (`crearClienteDeUnUso`, `src/lib/supabase.ts`), que guarda la sesión solo en memoria y no lee la URL: la sesión de la app no cambia. Confirmar la cuenta o el email cierra enseguida la sesión que abre Supabase (`signOut({ scope: 'local' })`) y pide ingresar; la recuperación sigue en *Recuperar la contraseña*. Cada link se canjea una vez aunque la pantalla se monte dos; un error de red deja probar de nuevo.
- *Captcha:* con `EXPO_PUBLIC_TURNSTILE_SITE_KEY`, registrarse, ingresar con email y pedir el link de recuperación muestran Cloudflare Turnstile (`Captcha.web.tsx`, que baja el script de Cloudflare solo en esas pantallas) y mandan el token a Supabase Auth (`captchaToken`), que lo verifica con la clave secreta cuando el captcha está activado en el proyecto. Cada token sirve para un intento: después se pide otro. Ingresar con Google no lo lleva. Sin la variable, o en la app nativa (que todavía no tiene el widget), no hay captcha.
- *Mails:* los de Auth (confirmar la cuenta, recuperar la contraseña, cambiar el email y enlace mágico) salen del SMTP propio con las plantillas de `supabase/templates/`, que se cargan en el proyecto con la API de gestión. El del enlace mágico no tiene link: la app no lo usa.
- *Recuperar la contraseña:* `resetPasswordForEmail` manda el link a `/auth/confirmar?…&type=recovery`. Al canjearlo, la sesión queda en el cliente de un uso (`empezarRecuperacionConLink`, `src/features/auth/recuperacion.ts`) y el layout lleva a `/auth/nueva-contrasena`, que muestra de qué cuenta es (`e***@gmail.com`) y ofrece "No es mi cuenta" (`cancelarRecuperacion`, que cierra esa sesión). Al guardar, `cambiarContrasena` hace `updateUser` en ese cliente y recién ahí pasa la sesión a la app con `setSession`. El link viejo (`?code=`, de las plantillas anteriores) todavía anda en el navegador que lo pidió: Supabase canjea el código y emite `PASSWORD_RECOVERY`, al que la app se suscribe al cargar el módulo, antes de montar. El mensaje al pedir el link es el mismo exista o no la cuenta.
- *Términos:* al registrarse con email, la casilla manda la versión aceptada en `user_metadata` y `handle_new_user` la guarda en `perfiles` con la fecha, si es la vigente. Quien entra con Google, o aceptó una versión anterior, acepta con `aceptar_terminos` antes de publicar, avisar, cambiar un estado, escribir o denunciar. La base lo exige en esas RPC y en las políticas de INSERT de `mensajes` y `denuncias`.
- *Perfil:* el nombre público (2 a 40) y la foto, que se comprime como las de los casos y va a `fotos/<uid>/`; un trigger exige que sea de esa carpeta.
- *Borrar la cuenta:* la app pide `fotos_para_borrar` (las de la carpeta del usuario menos las de lo que queda publicado), las borra con la API de Storage y llama a `borrar_mi_cuenta`, que aplica `limpiar_cuenta` y borra el usuario de Auth (solo el de `auth.uid()`). La persona elige si sus encontrados abiertos y lo que aportó a casos abiertos de otros quedan publicados sin autor (por defecto) o se borran; todo lo demás se borra, también sus perdidos aunque estén abiertos (sin la familia nadie podría cerrarlos ni confirmarlos) y el contacto de resguardo. Si se borra un usuario desde el panel de Supabase, un trigger en `perfiles` aplica la opción por defecto.

**Reportar un error.** En Perfil, con o sin cuenta, "Reportar un error" abre un formulario (un bloque que se carga al tocarlo): qué pasó (de 10 a 1000 caracteres), qué estaba haciendo y, con cuenta, una captura o, sin cuenta, un contacto. La app suma la pantalla anterior a Perfil (`src/lib/rutasRecientes.ts`), el user agent, el tamaño de la ventana, la plataforma y la versión (`app.json` más el commit del deploy). La captura se comprime como las fotos, sin miniatura, y va al bucket privado `capturas/<uid>/`. `reportar_error` valida, limita (5 por hora por cuenta y un tope global por hora sin cuenta, en `config_app`) y avisa a cada moderador. En **Moderación → Errores** se ven pendientes y resueltos con todo el detalle; la captura, con un link firmado de una hora. `resolver_reporte_error` lo marca resuelto con una nota opcional y, si quien lo mandó tenía cuenta, le avisa en Actividad.

**Instalar la app (web).** `public/manifest.webmanifest` (nombre, `start_url` "/", `display: standalone`, colores e íconos: los del logo de Spot, que `scripts/iconos-web.py` arma desde `assets/images/icon.png`) y un service worker mínimo (`public/sw.js`): Chrome lo pide para ofrecer la instalación. Solo responde las páginas, siempre desde la red, y no guarda nada. Un script en el `<head>` de `index.html` guarda `beforeinstallprompt` y `appinstalled` antes de que monte la app, y registra el service worker al terminar la carga. En Perfil, "Instalar la app" abre la ventana de Chrome o Edge, los pasos de Compartir en iPhone y iPad, o, en los navegadores de WhatsApp, Instagram y Facebook, cómo abrir el link en Chrome o Safari (`src/features/instalar/`). Instalada, o en la app nativa, no aparece.

**Atrás en web.** `Hoja`, `MenuOpciones` y `SelectorUbicacion` usan `useCerrarConAtras`. En web, cada hoja abierta suma una entrada al historial con la misma URL y una marca en `history.state`, y Atrás cierra la de arriba (`src/lib/historialHojas.ts`). Expo Router no se entera de esas entradas: los `popstate` que solo cierran hojas no le llegan. Cerrar desde la interfaz (X, Cancelar, Escape, enviar) quita la entrada con `history.go`, que es asincrónico; mientras tanto, lo que Expo Router escriba en el historial espera. Si la app navega con una hoja abierta, primero se quitan sus entradas, así no quedan huérfanas. Un botón de una hoja que lleva a otra pantalla (Editar el reporte, Ingresar, escribirle a alguien, borrar el reporte) usa `cerrarYNavegar`: cierra la hoja con `flushSync`, así su efecto empieza a quitar la entrada, y navega cuando terminó (`cuandoTermine`). Expo Router 58 navega dentro de una transición de React y, si la navegación empieza mientras la hoja quita su entrada, cambia la URL pero sigue mostrando la pantalla de antes (auditoría 2). Para eso el módulo reemplaza `pushState`, `replaceState` y `go` de `window.history`, y depende de cómo los usa Expo Router: al actualizar Expo o Expo Router hay que volver a recorrer los flujos de Atrás de `docs/PRUEBAS-MANUALES.md`. En Android, Atrás cierra la hoja con `onRequestClose` de `Modal`; en iOS no hay Atrás.

## Seguridad

- RLS en todas las tablas. Lectura pública de animales, avistamientos, historial y coincidencias, salvo los casos ocultos por moderación (solo quien lo publicó y los moderadores; una coincidencia, si se ven los dos lados) y, desde la 0027, el detalle de un caso reunido (avistamientos, historial, coincidencias y contactos: solo quien participó y moderación; el resto ve lo básico); todo lo personal (seguimientos, denuncias, notificaciones, conversaciones, mensajes, tokens) solo para su dueño o participantes.
- Permisos de tabla además de RLS: `anon` y `authenticated` no tienen INSERT, UPDATE ni DELETE sobre `animales`, `avistamientos` ni `cambios_estado`. En `perfiles`, `mensajes`, `notificaciones` y `denuncias` el UPDATE se concede solo sobre las columnas que la app cambia; `es_moderador` se asigna únicamente por SQL. En `mensajes` y `denuncias` también el INSERT está limitado a las columnas que manda la app (`leido_en`, `estado` y `created_at` toman su default).
- Storage: bucket público de lectura por URL; cada usuario escribe, borra y lista solo en `fotos/<uid>/` (el bucket no se puede listar entero: la política de lectura es solo para la carpeta propia). `publicar_animal` y `registrar_avistamiento` solo aceptan una foto que exista en esa carpeta, con el nombre que sube la app (`es_foto_propia`): nada de URLs externas ni de otros nombres. Una foto va en un solo avistamiento (índice único, salvo las URL de los datos de demo).
- Capturas de "Reportar un error": bucket privado `capturas`. Sube solo quien tiene cuenta, a `capturas/<uid>/`; leen quien la subió y los moderadores (con link firmado); borra solo quien la subió. `reportar_error` solo acepta una captura de la carpeta propia (`es_captura_propia`).
- `reportes_errores`: sin INSERT ni UPDATE desde la API; SELECT solo para moderadores. Los límites por hora están en la base, con un candado por cuenta (o por el tope sin cuenta) para que dos pedidos simultáneos no pasen el mismo límite.
- Muro de reencuentros: lo público sale solo de `contador_reencuentros`, `muro_reencuentros` e `historia_reencuentro`, que devuelven columnas fijas (la foto, el nombre si la familia quiso y no parece un contacto, la especie, los días, la frase y la fecha). `anon` no lee filas de `historias_reencuentro` (la RLS solo deja a la familia y a moderación) y `agradecimientos` no tiene permiso para `anon`. Quién ayudó y los agradecimientos no salen nunca en el muro ni en la vista previa. La frase y el mensaje se guardan con los teléfonos, links y emails tapados, y un check los rechaza si llegaran sin tapar.
- Nada de datos personales en tablas públicas. Contacto por mensajería interna o por lo que la persona decide compartir: `contactos_resguardo` (quien lo resguarda; en un perdido, solo para la familia) y `animales.contacto_familia` (la familia de un perdido, mientras el caso está abierto: al reunirse o vincularse se vacía). La app muestra este último siempre junto al aviso contra estafas, que aparece en todo caso abierto.
- `perfiles` se lee por columna: id, nombre público, avatar, `es_moderador` y fechas. Los datos de términos no.
- Términos vigentes aceptados para publicar, avisar, cambiar estados, escribir y denunciar, validado en la base.
- Las validaciones con un usuario que puede faltar (casos sin autor) usan `is distinct from`: con `<>` o `not in`, un null hace que la condición no se cumpla y la validación se saltea.
- Borrar la cuenta solo actúa sobre `auth.uid()`. Las fotos se borran con la API de Storage, con la sesión del usuario; nunca por SQL. Lo mismo al borrar un reporte, que solo puede borrar quien lo publicó.
- La vista previa del link (`api/vista-previa.ts`) lee `animales_detalle` con la clave pública, como un visitante sin cuenta, y pide solo las columnas que usa: ni el contacto ni quién publicó llegan a la función. Tampoco usa la descripción libre, donde alguien pudo haber escrito un teléfono, ni la ubicación. De un caso reunido, solo el nombre (si se mostró) y la especie.
- La descripción y el nombre de un caso no se leen de la tabla `animales` (permiso por columna, 0027): la RLS filtra filas, no columnas, y sin esto cualquiera sacaría la descripción de un caso reunido, o el nombre que la familia no mostró, pidiendo la tabla directo.
- Claves: la publishable (`EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `sb_publishable_…`) va en la app y en la vista previa (pública por diseño); la `anon` legacy queda de respaldo mientras exista (`elegirClave`, `src/lib/env.ts`). Supabase deja de aceptar la anon a fin de 2026. La función `reconocer` usa la clave secreta que Supabase pone en su entorno (`SUPABASE_SECRET_KEYS`, o la legacy `SUPABASE_SERVICE_ROLE_KEY` mientras exista) y `ANTHROPIC_API_KEY`, un secreto de la función; ninguna está en el repo. `vision_secret` vive solo en `config_app` (32 bytes en hexadecimal): la base lo manda en `X-Vision-Secret` y la función lo compara con el de la base; un header con otra forma lo rechaza sin consultarla. Google en el dashboard de Supabase.
- Notificaciones en el celular: la clave VAPID pública va en la app (`EXPO_PUBLIC_VAPID_PUBLIC_KEY`, pública por diseño); la privada es un secreto de la función `avisar` (`VAPID_PRIVATE_KEY`, con `VAPID_PUBLIC_KEY`), nunca en el repo. `avisar_secret` vive en `config_app`, con el mismo esquema que `vision_secret`. La función solo manda a los servicios de push de los navegadores (lo revisan la base y la función: una suscripción no puede apuntar a cualquier URL) y lo que manda va cifrado para cada navegador. El texto se ve en la pantalla bloqueada: solo el nombre del animal (si no parece un contacto) o la especie, nunca nombres de personas, mensajes ni lugares.
- Captcha (Cloudflare Turnstile): la clave del sitio es pública (`EXPO_PUBLIC_TURNSTILE_SITE_KEY`); la secreta está solo en Supabase Auth, que verifica cada token. Protege registrarse, ingresar con contraseña y recuperar; Supabase exige el token también en OTP, enlace mágico y reenviar, que la app no usa.
- Google: el ID de cliente web es público (`EXPO_PUBLIC_GOOGLE_CLIENT_ID`); el secreto de cliente está solo en el proveedor de Google de Supabase, que lo usa para el respaldo con `signInWithOAuth`. Para `signInWithIdToken`, Supabase acepta solo tokens emitidos para los ID de cliente de su lista ("Client IDs") y con el nonce que corresponde ("Skip nonce checks" apagado).
- Mails: las plantillas no incluyen nada que escriba la persona (ni el nombre público), así nadie usa el registro para mandar texto propio a un email ajeno.
- Reconocimiento con IA: a Anthropic van solo las fotos (la versión mediana o la original, dentro del pedido; las de demo de otros sitios, igual) y los datos del animal (tipo, tamaño, color y collar declarados, y lo que se vio en las fotos). Nunca nombres, contactos, mensajes ni la descripción libre. Las instrucciones le dicen a Claude que ignore cualquier pedido escrito en una foto o en los datos, y cada respuesta se valida contra su esquema. Las descripciones, las comparaciones y el uso solo los leen los moderadores; la función los escribe con RPC que solo puede llamar `service_role`.

## Mapa

Estilo `positron` de OpenFreeMap (gratis, sin clave, datos de OpenStreetMap bajo ODbL), descargado una vez por sesión y recoloreado en el cliente con los tokens de mapa del esquema claro u oscuro (`estiloBase.ts` y `recolorearEstilo.ts`). Los animales van en una fuente GeoJSON con clustering: los clusters son círculos `inverso`; cada punto suelto que se ve lleva un marcador con su miniatura (48 px, 58 el seleccionado), anillo del color del estado, colita y, en los perdidos, halo (`MARCADOR` en `estilosCapa.ts`). En web es un elemento del DOM (`Marker` de MapLibre GL JS); en nativo, `Marker` de MapLibre React Native con `MarcadorFoto`. Debajo de cada foto hay una zona táctil casi transparente (la capa `animales-punto`, corrida hasta la foto) que recibe el toque y dice qué puntos se ven; el seleccionado se dibuja aparte aunque un cluster lo tape. Recorrido como línea punteada con el último punto en el color del caso. El mini mapa del detalle abre el mapa en grande del recorrido (`/animal/<id>/mapa`, `MapaRecorridoGrande`): puntos numerados en orden, los aproximados (donde se perdió y el resguardo, que la base guarda redondeados) como una zona de 110 m, y una tarjeta con Anterior y Siguiente. La pantalla ordena y arma el GeoJSON (`src/features/mapa/recorrido.ts`); la vista inicial y el radio de la zona los calcula el mapa (`src/features/mapa/encuadre.ts`), así en web cada parte queda en su bloque. En el celular, la hoja "Cerca tuyo" se pliega y despliega (arrastre con `PanResponder`, posición con `Animated`, guardada en el dispositivo; reglas en `src/features/mapa/posicionHoja.ts`): plegada, el botón de mi ubicación baja con ella y los márgenes del mapa (y con ellos los créditos) pasan al alto de la barra. Las capas salen de `estilosCapa.ts`, que recibe la paleta. Colores y medidas en `docs/DISENO.md`. Dos implementaciones con el mismo contrato (`src/components/mapa/tipos.ts`):

- **Web:** `maplibre-gl` (BSD-3), que pesa casi 1 MB, en un bloque aparte. Los `.web.tsx` (`MapaReportes`, `MapaRecorrido`, `MapaRecorridoGrande`, `MapaSelector`) son livianos y cargan las implementaciones (`…GL.tsx`) con `lazy` e `import()` desde un único módulo, `mapasWeb.ts`; si se importaran por separado, Metro pondría MapLibre en el bloque común de la carga inicial. Mientras tanto muestran el fondo del mapa, del mismo tamaño. El mapa principal y el del detalle esperan a que la pantalla muestre sus datos y sus fotos prioritarias (`useCargarMapa`); el selector y el mapa en grande cargan enseguida. El worker y los estilos de MapLibre se sirven desde `public/` (los copia `scripts/copiar-a-public.js`): el bloque pide los estilos al cargarse, así no están en el `<head>` de la carga inicial. El mapa queda siempre al norte: ni el mouse, ni dos dedos, ni el teclado lo rotan o inclinan (`crearMapaWeb`), como en nativo.
- **Nativo:** MapLibre React Native (MIT) en los `.tsx`. Exige development build (no corre en Expo Go).

## Carga inicial en web

Casi todos llegan desde un link de WhatsApp a `/animal/<id>`, en un navegador interno que no comparte la caché: la primera carga es la que importa. El orden es: lo que se ve sin JS, después los datos y las fotos de la pantalla, y al final lo accesorio (el mapa y la tipografía).

- **Sin JS:** `public/index.html` trae la pantalla de carga (`#carga`, solo HTML y CSS, con el fondo de la paleta clara u oscura y el logo en SVG en línea) y la app la saca cuando dibuja contenido (`src/lib/pantallaCarga.ts`). También abre de antemano las conexiones a Supabase (una para la API, con CORS, y otra para las fotos de Storage, sin CORS) y a OpenFreeMap (`preconnect`). La URL de Supabase está escrita ahí: si cambia el proyecto, se cambia también en `index.html`.
- **Datos:** `_layout` pide los datos de la ruta de entrada apenas carga, sin esperar a que lleguen sus pantallas (`src/features/reportes/precarga.ts`): los casos del mapa en `/` y `/casos`, y el caso, sus avistamientos y su historial en `/animal/<id>`. Apenas se conoce la foto del caso, se empieza a bajar con prioridad alta. Las pantallas usan las mismas claves y no vuelven a pedir lo que tiene menos de 30 s.
- **Fotos:** las que se ven al abrir (las primeras tarjetas y la foto del caso) se piden enseguida y con prioridad alta; el resto, cuando se acercan a la vista. Mientras bajan, quedan anotadas en `src/lib/fotosPrioritarias.ts`.
- **Mapa y fuentes:** cuando terminan las fotos prioritarias y el navegador está desocupado, se cargan MapLibre, el estilo del mapa y las fuentes (`useCargarMapa`). En las pantallas sin mapa, las fuentes se activan a los 4 s. Las fuentes las declara `index.html` con `font-display: swap` y empiezan apagadas (`media="not all"`); hasta que llegan, el texto usa la pila del sistema. En web no se usa `expo-font` para ellas: hacía esperar a la app y bajaba cada una dos veces.
- **Lo que se abre con un botón va en un bloque aparte** (`lazy` e `import()`): el formulario de errores, la sección Errores del panel, las hojas de instalar, la hoja de la historia con su generador (`HojaHistoria`), las notificaciones del celular (`AvisosCelular`, con el código del navegador aparte en `celular.web.ts`) la hoja de denuncia (`ModalDenuncia`, que comparten el caso y el muro) y, en Ingresar y Registrarse, Google (`IngresoGoogle`, que recién ahí baja el script de Google). Ojo con `__common`: un módulo que usan dos bloques aparte (o un bloque aparte y una pantalla) Metro lo pone ahí, y ese bloque se baja siempre. Por eso mandar un reporte (`src/features/errores/api.ts`) y moderarlos (`moderacion.ts`) están en archivos distintos.
- **Muro de reencuentros:** todo en bloques aparte. `components/reencuentros/Reencuentros.tsx` es uno solo para `/reencuentros`, `/reencuentros/<id>` y "Cómo volvió" en el detalle de un caso reunido; el formulario de contar es su ruta. El contador va en otro bloque chico (`components/reencuentros/Contador.tsx`, con la consulta de `features/reencuentros/contador.ts`): de ahí cargan con `lazy` la tarjeta de "Cerca tuyo" entera (cuando el mapa ya mostró sus casos; en el bloque del mapa queda solo el `lazy`) y el muro su `ConContador`, que lo dibuja a su manera. Los módulos se separan por quién los usa: `claves.ts` y `historia.ts` (los usa también la precarga de `/reencuentros/<id>`), `muro.ts` (el bloque del muro, con su "ya denunciaste"), `contar.ts` y `reglas.ts` (el formulario), `ayude.ts` (Perfil); la denuncia se manda desde `features/denuncias/denunciar.ts`, que solo usa la hoja. A la carga inicial le suman solo los textos de `es-UY.ts` y esas dos claves (medido en `docs/reportes/2026-10-22-reencuentros.md`).
- **Instalar:** `index.html` tiene un script chico que guarda el aviso de instalación y registra el service worker al terminar la carga; el manifest y los íconos los pide el navegador después.
- **Lo que solo usa una acción** se importa al usarlo (`import()`): `expo-image-manipulator`, `expo-crypto` y `expo-file-system` al subir una foto (`src/lib/fotos.ts`) y `expo-location` en nativo (`src/lib/ubicacion.ts`). El polyfill de URL que necesita Supabase es solo nativo (`src/lib/polyfills.ts`).

## Despliegue

Web estática en Vercel: `npx expo export -p web` genera `dist/` (modo `single`; `vercel.json` reenvía todas las rutas a `/`). La única excepción: los pedidos de `/animal/<id>` y `/reencuentros/<id>` de bots de vista previa van a la función `api/vista-previa.ts` (Node, sin dependencias). El preset del proyecto es **Other** y `.vercelignore` deja afuera `services/`, para que Vercel no detecte Python. Variables `EXPO_PUBLIC_*` en Vercel (la función usa las mismas): la URL y la clave pública de Supabase, y opcionales el sitio, el estilo del mapa, la clave del sitio de Turnstile y el ID de cliente web de Google (solo en Production: las vistas previas no son orígenes autorizados de Google y usan el botón de respaldo). Van dentro del build: cambiar una pide un deploy nuevo. El `buildCommand` de `vercel.json` suma `EXPO_PUBLIC_COMMIT` (de `VERCEL_GIT_COMMIT_SHA`) y `EXPO_PUBLIC_FECHA_BUILD`, que el formulario de errores manda como versión; se leen solo en ese bloque, para que cada deploy no cambie el bloque inicial. `public/manifest.webmanifest`, `public/sw.js` y `public/iconos/` se sirven como archivos (los íconos los genera `scripts/iconos-web.py`). `public/robots.txt` se sirve como archivo: Vercel busca primero en los archivos y después aplica los rewrites. Lo que genera el export en `/_expo/static` y `/assets` lleva un hash en el nombre, así que `vercel.json` lo manda con `Cache-Control: public, max-age=31536000, immutable`; `index.html` y `api/` se revalidan como siempre. Todo el sitio lleva encabezados de seguridad: `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` y una CSP en modo reporte con los orígenes que usa la app y los hashes de los dos scripts en línea de `index.html` (`docs/DECISIONES.md`, "Encabezados de seguridad"). Las fotos se suben con `cacheControl` de un año: el nombre es un UUID y nunca se reescriben. Supabase en su plan gratuito; migraciones con `supabase db push` o pegadas en el SQL Editor. Notificaciones en el celular: la Edge Function `avisar`, desplegada con `npx supabase functions deploy avisar` (`verify_jwt = false`; la protege `X-Avisar-Secret`), con `VAPID_PUBLIC_KEY` y `VAPID_PRIVATE_KEY` como secretos de la función y `EXPO_PUBLIC_VAPID_PUBLIC_KEY` en Vercel; pasos en `docs/reportes/2026-10-22-avisos-historias.md`. Reconocimiento: la Edge Function `reconocer`, desplegada con `npx supabase functions deploy reconocer` (`verify_jwt = false` en `supabase/config.toml`; la protege `X-Vision-Secret`), con `ANTHROPIC_API_KEY` como secreto de la función (`npx supabase secrets set`). Pasos en `docs/reportes/2026-10-20-reconocimiento-ia.md`. El servicio de embeddings (`services/vision`) no se despliega.
